等待结束，登记也消失了吗？

只回答一个问题：Any 已有胜者，其他等待记录的生命周期何时结束？

先辨认真实对象

本单元观察 dev 开发 worktree，不把新增机制当成 teaching 分支原有行为。一次组合等待有一个登记对象；Actor 的消息索引保存匹配引用；worker 的 timer 堆保存截止时间和登记关联。把登记标成 inactive 只改一个状态，不会自动删除另外两个容器中的项。

先预测：等待包含“消息、10 分钟后的 timer、已经过期的 timer”，反复执行 10000 次。即时返回后，消息索引和 timer 堆应分别留下多少旧项？

最小实验

Any(message(unique_id), timer(now + 10min), timer(now - 1s))
→ 检查返回原因与胜出分支
→ 检查 Actor 消息索引
→ 检查 owner worker timer 堆

还要覆盖登记到一半抛错，以及真正暂停后由消息或 timer 唤醒；只测即时返回会漏掉恢复路径。

预测后再看代理实测

同一测试用旧版本头文件/库构建：失败，提示 message registration retained。当前实现：1/4 worker 各执行 10000 次即时胜出、1000 次登记失败回滚，以及真实消息和 timer 唤醒，相关登记均清空。完整测试 14/14、专项重复 20/20；不是性能不劣化证据。

按源码核对更新时间

第一手资料是本轮测试、installWait / cleanupWait和await 恢复路径。即时完成和安装失败由回滚守卫清理；真正挂起的等待，在固定 owner 恢复时、返回业务调用前清理。计时仍使用现有条件变量，不切换 timerfd。

本轮没有修改 timer 调度策略；补齐的是中断时缺失的测试和可重跑证据。撤销等待不等于取消其关联的业务工作。
