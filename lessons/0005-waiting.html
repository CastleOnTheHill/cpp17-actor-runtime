05 / 24 · 多一种状态，少一次无效运行

暂时不能运行的任务

唯一主问题：条件未满足的协程应该放在哪里？

沿用第 4 章真协程；时间采用模拟 tick，不等待真实秒数。

从“让别人先跑”到“我还不能跑”

第四章的 yield 只表示让出一次，之后仍可再次被选择。如果 A 等待到时刻 5 才能继续，把 A 每次都放回 ready，就会不断恢复它去检查“到了没有”。这叫反复检查条件，不是我们要构建的等待登记。

本章让 A 在时刻 0 等待，B 仍能执行；到时前 A 不被选中，到时后 A 才重新获得候选资格。重点是状态变化，不是实现高精度定时器。

A · 等待者仍然存在

离开 ready，不等于释放协程

状态含义本模型的归属
Ready可以运行，尚未获选ready 中有一个 ID
Running当前线程正在此调用链上running 指针
Waiting等待条件，不能直接恢复Fiber 仍持有栈/context，并记录 deadline
Done业务调用链已经结束等待 scheduler 回收，不能恢复

先不新增复杂等待容器：共享外壳在 Fiber 上保存 deadline，推进时间时扫描 Waiting 项。扫描是教学选择，不是高效定时器数据结构；之后可以换最小堆，而不改变基本状态规则。

ready 为空只说明“现在没有候选者”，不说明“所有任务完成”。等待中的栈和资源仍然占用着。

B · 登记与唤醒是两次转换

deadline 到了，也只是重新入队

// A 中执行：
deadline = now + duration;
state = Waiting;
swap_to_scheduler();

// scheduler 推进模拟时间时：
if (state == Waiting && deadline <= now) {
    state = Ready;
    ready.push_back(id);
}

“到时”没有让 A 自动成为 Running；要等 scheduler 再选它。改变状态再入队，也让下次重复扫描不再把同一个 Waiting 项入队第二次。这个模型一次只有一个计时等待，没有消息与超时竞争；旧事件 generation 留到第 17 章。

时间不是线程 ·

① now=0：A 登记 deadline=5

A 切回 scheduler，状态 Waiting，ready 只剩 B。A 的栈还在，但没有被恢复的资格。

② now=0：B 完成

ready=[]，A 仍 Waiting。此时 step 返回 false；只有 B 的完成记录。不能据此销毁 A。

③ advanceTo(4)

4<5，A 不入队。模拟时间只是整数，不是 OS sleep；A 没有反复恢复做检查。

④ advanceTo(5)

A 从 Waiting→Ready，只入队一次。再次 advanceTo(5) 不增加第二个 ID。随后 step 才恢复 A，A 从原 sleepFor 后继续。

量纲不要混

now=0 tick、duration=5 tick，则 deadline=5 tick；是否到期比较两个时刻，不把 duration 直接和某个真实 Unix 时间比较。本实验 tick 没有绑定秒，因此输出 @5 不代表程序耗时 5 秒。

run 的便捷规则是：ready 为空且仍有等待者时，将模拟时间跳到最早 deadline。ready 一直非空则不会自动推进；它既不模拟 CPU 耗时，也不提供真实时间下的公平保证。

C · 把边界固定住

预测三个可重复场景

./labs/build/ch05_waiting deadline
./labs/build/ch05_waiting same-deadline
./labs/build/ch05_waiting zero
预测之后核对断言

deadline 输出 A waits@0、B runs@0、A resumes@5，程序还检查 @4 不唤醒、@5 重复扫描不重复入队。same-deadline 在 @3 依创建顺序恢复 A、B。zero 把 sleepFor(0) 规定为 yield，因此输出 A1、B、A2，模拟时间仍为 0。

同截止时刻的顺序、零时长是否让出，都是本实验约定，不从名字就能推断，也不代表实际框架零时长 await 一定切出。

构建变式：先登记晚截止，再登记早截止

在个人副本中让 A 等到 7，B 等到 2。先让两者进入 Waiting，再推进到 1、2、6、7。每一步断言 ready 数量、完成数量和保留栈数。输出顺序应由截止条件决定，而不是仅由创建顺序决定。

再反向构造错误：把 Waiting 像 Ready 一样直接入队，看看 @0 就恢复的断言如何失败。只在测试副本中改；这个有限反例不需要 sleep，更不要用忙等无限循环。

源码证据与实际框架差异

读 sleepFor、advanceTo、run及边界测试。切出机制仍遵循上下文切换手册，等待策略来自本章代码。

实际 CoroutineContext::await 先 installWait，再设 Waiting 并切出；条件已满足可能直接返回。workerLoop 使用 steady_clock 和条件变量等待，且当前 teaching 实现只有未选中普通 job 时才检查到期 timer；持续 job 压力下不能承诺定时器准时触发。

本实验没有阻塞 OS 线程。将来使用条件变量让空闲 worker 等待，是在线程层面减少空转；它与“某一条协程 Waiting”是两个层次。

唯一过关题

A 正在等待 deadline=5，B 已结束，ready 为空。请说明 now=4、now=5 但尚未 step、step 恢复 A 这三个时刻，A 的状态、栈是否存在、谁负责推进分别是什么。为什么把“ready 为空”作为整个系统退出条件会出错？

作答后自评

@4 是 Waiting，@5 扫描后是 Ready，step 切入才是 Running；三者都还需要这条调用链的栈。时钟推进与扫描由 scheduler 执行，选中由 step 完成。ready 空时仍有 Waiting，提前退出会遗留未完成调用链。若说不清 @5 与 Running 的差别，只重做两次 advanceTo(5) 的例子。
