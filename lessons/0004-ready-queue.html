04 / 24 · 把两次手动 resume 变成一个循环

谁来选择下一条协程？

唯一主问题：A、B、C 都能运行时，下一步由谁决定？

前置：能解释第三章两次 swap 的方向。本章仍只有一个 OS 线程。

从已有部件增加一个职责

第三章的 main 写死了“resume A，运行 B，再 resume A”。栈切换解决了“怎样继续”，却没有解决“有多个候选时选谁”。现在不改切换原理，只把 main 的选择过程变成一个可重复执行的规则。

本章产物是一条 FIFO ready 队列。你先用纸片实现调度，再把纸片换成协程 ID。暂时忽略共用外壳里的 sleepFor 与 collect；它们分别留给第五、六章。

A · 真实对象与状态

队列装的是候选者，不是调用栈

对象存什么更新时机
Fiber独立栈、context、执行状态进入时 Running；主动 yield 后 Ready；入口返回后 Done
ready 队列可以被恢复的 Fiber ID创建时入尾；选择时出头；让出后重新入尾
scheduler选择与检查状态的普通代码只有协程把控制交回后，才有机会选下一个

把 ID 放进 ready，并不会复制栈，更不会立刻执行。它只声明：此协程具备运行条件。队列顺序是本实验选择的策略，不是 ucontext 提供的功能。

关键不变量：一个 Ready 协程在 ready 中恰好出现一次；Running 和 Done 不在其中。若完成者又被入队，就可能恢复已失效现场。

B · 一轮调度只有四步

出队 → 恢复 → 交回 → 决定去处

id = ready.front(); ready.pop_front();
fiber[id].state = Running;
resume(fiber[id]);              // 期间 scheduler 暂停
if (fiber[id].state == Ready)   // yield 回来了
    ready.push_back(id);
// Done 不重新入队

这是算法摘录，不是可直接编译的完整库。真正保存/加载现场的仍是第三章的 swapcontext。返回 scheduler 后再检查状态，这个检查点才把“切换机制”与“调度策略”接起来。

用队列预测 ·

① 初始 [A, B, C]

取 A，A 输出 A1 后 yield。此时 A 没完成；回 scheduler 再把 A 入尾。

ready = [B, C, A]

② B、C 各让出一次

B 输出 B1；C 输出 C1。每次都出头、运行一段、入尾。

ready = [A, B, C]

③ A 第二段完成

A 从旧 yield 后继续，输出 A2，入口返回。状态 Done，不再入队。

ready = [B, C]

④ B、C 也完成

输出 B2、C2；队列为空。本章没有等待者，所以所有任务结束；第五章会让这句话不再普遍成立。

ready = []

先限制你能声称的“公平”

FIFO 只能让已经排队的候选者按此规则获得机会。如果 A 不交回控制，scheduler 就无法执行队列操作。本实验 no-yield 模式只让 A 连做三步，避免真的把程序卡死；无穷循环会让 B 永久没有机会。

若有 N 个持续 Ready 的任务，且每一段都在有限时间内交回、没有额外插队，一次轮转才有 N 次选择。这里计算的是选择次数，不是毫秒；没有片段耗时上界就推不出延迟上界。

C · 构建、反例与反馈

先用纸片调度，再运行真正的栈

画三个任务，每个任务两段。用 A/B/C 三张纸表示 ready：自己执行一次“移出队头、判断是否结束、必要时放回队尾”。把每一步队列和输出写下来，再运行：

cmake -S labs -B labs/build
cmake --build labs/build -j4
./labs/build/ch04_ready_queue round-robin
./labs/build/ch04_ready_queue no-yield
./labs/build/ch04_ready_queue empty
写完预测后核对

round-robin：A1、B1、C1、A2、B2、C2；no-yield：A1、A2、A3、B1；empty：没有任务输出，直接 PASS。程序使用真实有栈协程并断言完整轨迹，最后确认完成后再次 step 返回 false。

自己构建的改动

在个人副本中，让 A 有三段、B 一段、C 两段，只有尚有下一段时 yield。先推导输出，再修改断言。之后把“让出后入尾”暂改成“入头”，观察连续让出的 A 如何影响 B。恢复 FIFO 并说明两个策略的差别，不把任一策略称为万能公平。

构建工单说明该挖空哪个函数、需要保留什么安全外壳。请不要修改第二章已有练习。

实现证据与框架映射

本章测试与业务体；共享外壳只读 spawn、step、yield、entry。context 通过 unique_ptr 的指向对象保持地址稳定。

实际框架 workerLoop 同时检查 localQueue、globalQueue 和 timers，并不是一条简单的全局 FIFO。resumeFiber 还检查 owner 和 FiberState；不要根据本章轨迹推断多 worker 的全局消息顺序。

唯一过关题

初始 ready=[A,B]，A 每次执行都 yield，从不结束；B 执行一次就结束。在 FIFO 入尾和改成入头两种策略下，前四次选择分别是谁？如果 A 连第一次 yield 都不执行，两种队列策略又为什么都救不了 B？请沿“谁掌握控制权”解释。

作答后自评

入尾的选择为 A、B、A、A；入头为 A、A、A、A。A 不交回时 scheduler 不能执行第二次选择，修改队列没有作用。若只能背出序列却说不清控制权，回到第三章的 swap 返回点。
