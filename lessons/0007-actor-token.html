07 / 24 · 给并发执行增加一个约束

Actor 的执行令牌

唯一主问题：多个 worker 为什么仍能串行访问同一个 Actor？

本章首次运行多个 OS 线程；暂不在这些线程之间搬运有栈协程。

先不要把 Actor 当成一条专属线程

你已经理解 Actor 的概念。现在只追问实现上的一条承诺：同一个 Actor 的两个执行片段，不能同时访问它的业务状态。第 4 章只有一个线程，这条性质自然成立；加入多个 worker 后，它需要一个具体机制。

我们先把协程栈放在一边，用普通 handler 隔离观察串行访问。这个刻意拆分避免一次混进“锁住 Actor”与“Fiber 必须在哪个 owner 上恢复”两个问题；owner 留到第 18 章。

A · 队列安全不等于业务安全

取任务的时候没打架，处理时仍可能重叠

假设两个 worker 都从线程安全队列取到了不同任务，但两个任务属于同一个 CounterActor。队列不会把同一个任务给两个人，这仍不保证他们不会同时执行 value=value+1。

顺序模拟错误交错，不执行数据竞争 ·

① worker A 获得任务 1

A 读 value=0，将 0 暂存为自己的计算输入。它还没有写回。

② worker B 获得任务 2

B 也读到 value=0。取出的任务不同，但共享的是同一份 Actor 状态。

③ A 写回 1，B 随后写回 1

两个任务都处理过，结果却只有 1，不是 2。queue-only-model 用单线程按此顺序模拟；不要把真实未加锁 C++ 代码的行为保证为恰好 1。

这里演示的是缺少约束会允许的逻辑交错。真实多线程并发读写普通 int 若没有同步，会构成数据竞争；不能用“多跑几遍大多正确”证明合法。练习不会让你制造这种未定义行为。

B · 令牌不是神秘的新实体

本实现中，它就是 Actor 所属的 mutex 所有权

对象保存什么更新者
execution mutex当前独占所有权worker 在业务片段前获取，片段退出时释放
valueActor 的业务计数只由持有 execution 锁的 handler 访问
任务分配计数 next下一个未分配任务编号多个 worker 原子领取；它不保护 value
void handle() {
    std::lock_guard<std::mutex> token(execution);
    int before = value;
    // 这里即使 OS 把线程切走，锁的所有权也不会自动消失
    value = before + 1;
} // token 析构，释放锁

“执行令牌”是教学称呼，不是另建一条消息、一个 bool 或一条线程。mutex 的独占与同步语义提供互斥基础；程序必须把所有相关访问都放在这条边界内，才能兑现 Actor 串行约束。

锁的范围比“有没有锁”更重要

只锁读、解锁后计算、再锁写，仍可能丢失更新；要保护整个读改写业务片段。实验在持锁期间调用 std::this_thread::yield，仅给 OS 一个调度提示，并不释放 mutex，也不是我们的协程 yield。

异常退出时 lock_guard 析构，所以后续任务仍能进入；但这不意味着异常会回滚此前已经写入的业务数据。本例故意在修改 value 之前抛出，以便清晰验证“失败一条，成功其余条”。

不要持有普通非递归 mutex 后，在同线程再次调用会锁同一 mutex 的 handler；也不要持锁等待必须由同一 Actor 才能完成的操作。串行机制解决互斥，不自动解决死锁与长任务阻塞。

C · 从模型反例到真实多线程

用 1 / 4 worker 验证同一条约束

./labs/build/ch07_actor_token queue-only-model
./labs/build/ch07_actor_token 1
./labs/build/ch07_actor_token 4
./labs/build/ch07_actor_token throw
预测后检查结果

queue-only-model 显示两次读 0 后结果 1。1 与 4 worker 都应 applied=2000、errors=0。throw 用 4 worker、让任务 0 失败，应 applied=1999、errors=1；后续处理没有因异常遗留锁而卡住。

每个 handler 内用原子 active 计数检测重叠；value 本身仍是普通 int，依靠 execution 锁保护。主线程只在所有 join 完成后读取结果，不在工作线程写入期间偷看。

四线程测试不保证每个线程都获得相同份额，也不保证一定在多核同时执行；断言针对互斥和完整处理，不是吞吐或公平性。

构建任务：把边界画在代码上

从个人副本挖空 handle 的 lock_guard，先不要运行，标出必须共同保护的读、改、写，再补回正确作用域。然后新增第二个 CounterActor，各自拥有 execution mutex，交错分配两组任务，验证每个 Actor 各有正确计数。

这证明锁属于 Actor 而不是整个系统。若想观察两 Actor 可同时进入业务片段，需要专门的受控同步测试，不能仅从一次执行耗时猜测；本章没有声称已验证跨 Actor 并行度。

对照实际 teaching 分支

教学代码采用阻塞 lock_guard，容易看清作用域。实际 ActorControl 含 executionMutex 与 mailboxMutex；processJob 用 try_to_lock，没拿到就重新排队而非直接执行。

实际锁覆盖消息分发或一段 resumeFiber；协程 await 切回 scheduler 后，processJob 收尾释放锁。注意：协程暂停保留的是自己的栈，不是永远保留 Actor 的 execution 锁。此后另一个片段可修改 Actor 状态，所以跨 await 的业务不变量需要重新检查。

唯一过关题

W1 和 W2 已各自安全取出一个属于同一 Actor 的任务。为什么此时不能直接同时运行？请给出一个丢失更新的交错，再指出 execution 锁必须覆盖哪一段。W1 在锁内被 OS 暂停时，W2 是否就能进入同一 Actor？

作答后自评

安全领取只保护任务分配，不保护共同的业务状态。两者读 0 再各写 1是模型反例；整个读改写片段必须在同一个 Actor 的锁内。OS 暂停 W1 不会帮它解锁，W2 仍不能获取该锁。若把锁与线程生命周期混淆，只跟踪一次 lock/unlock 的位置。
