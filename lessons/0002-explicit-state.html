02 / 24 · 第一个可继续的部件

把“下一步”存成数据

这次只回答：不保留调用栈，怎样让一个任务跨多次调用继续？

前置：已能独立解释 return 与对象生存期。不使用 ucontext 或 C++20。

从第一章的缺口出发

第一章说明：不能指望普通函数返回后，旧的局部对象和旧的执行位置仍可恢复。现在反过来想：如果任务还要继续，我能不能把必要信息主动保存到一个尚未销毁的对象中？

本章只构建一个两段任务。你要让输出顺序成为 A before=41 → B ran → A after=42。A 的两段之间确实执行 B，但整个程序仍是一个线程，完全按 main 的调用顺序运行。

A · 先推导需要哪些状态

要续跑，至少知道“做哪段”和“带什么”

假设只保存 value=41。第二次调用时，程序怎么知道应打印 before 还是应该加一？它不知道。所以还需要 phase，表示下一次要执行的阶段。

反过来，只保存 phase、不保存要继续计算的 value，也不够。我们将两者放进 Task 对象。这个对象由 main 创建，直到多次 next 完成后才销毁；next() 自己每次仍是普通调用、普通返回。

成员保存什么谁更新
phaseStart / AfterPause / Finishednext 执行完对应一段后更新
value要跨调用保留的业务整数构造时初始化，第二段加一

Task 也可以是 main 的自动局部对象，不必放堆上。它只是要比每次 next 调用活得久。这里“持久”仅指跨这些调用，不是写入磁盘。复核依据：自动存储期，以及本章 C++17 实现。

next 返回的 Step 告诉调用者“这一步的结果”；成员 phase 告诉任务“下次从哪一段开始”。两个 enum 的职责不同，不能只保存返回值就假定任务记住了进度。

B · 从状态表生成代码

先写转换规则，再写 if

调用前 phase本次副作用调用后 phase返回
Start记录 A before=valueAfterPauseSuspended
AfterPausevalue 加一，记录 A after=valueFinishedDone
Finished无FinishedDone

本例 Finished 设计为不再发生副作用的终态。第二次调用已经完成；第三次调用没有重做第二段。这是你要建立的约定，不是编译器自动替你生成的性质。

Task task(41);
task.next(log);          // A 的第一段
log.push_back("B ran"); // main 选择运行 B
task.next(log);          // A 的第二段
task.next(log);          // 已完成，不再追加输出

这段 main 就承担了最简的“选择下一步做什么”的调度职责。它没有被操作系统主动抢占成另一个任务；只是在 A 返回后调用别的代码。本章尚无 ready 队列，也没有消息或定时器。

观察保存的信息 ·

① 尚未执行

Task 存在：phase=Start，value=41。没有任何 next 调用正在进行。

② 第一次 next 已返回

Task 仍存在：phase=AfterPause，value=41。next 的这次执行已结束；不是一条暂停的调用栈。

③ B 执行完毕

Task 的两个成员没变。谁来调用第二次 next？是 main；不是任务自己神秘地醒来。

④ 第二次 next 已返回

进入一个新的 next 调用，根据成员选择第二段：value=42，phase=Finished。以后再调只返回 Done。

第一级提示：只告诉你控制结构

首先检查 phase 是否 Start；执行第一段后更新 phase 并立刻 return。然后检查是否 AfterPause；第二段完成后设置 Finished。其余路径直接返回 Done。

第二级提示：检查变量的归属

请使用成员 value_，不要在 next 中每次重新声明 int value=41；请使用成员 phase_，不要把它放在每次重新初始化的局部变量里。完成不等于重置。

同机制变式：做第三段

在自己的练习副本中增加第三段：第二次先加 1 并暂停，第三次再乘 2 并完成。main 在两次暂停处都插入 B。输入 10 应记录 10、11、22；第四次调用不得再改状态。先修改状态表，再修改代码和断言。

验收不是“输出能凑对”：你需要说明每个成员为何必要、每次 next 仍会返回，以及 Task 若提前销毁，为什么后续调用不再合法。

你给 next 新增了局部 Guard g。第一次 next 返回 Suspended 后，g 会不会析构？第二次 next 为什么还能接着做任务？请给出“本次调用结束”到“任务进度仍然存在”的完整因果链，并说明如何保证完成后不再重复加一。

写完后自评

g 会在正常 return 离开作用域时析构。保留的是 Task 的 phase 与 value，不是 next 的栈；第二次从 next 入口重新进入，依据 phase 选择分支；Finished 阻止重复副作用。若答“g 不析构，因为任务暂停”，说明仍混淆任务状态与函数调用，退回第一章的 Guard 实验。

把练习 diff 和闭卷解释发给我。通过后才增加第三章的一个新能力：在 inner 的深层调用中暂停，仍保持其自动局部对象存活。
