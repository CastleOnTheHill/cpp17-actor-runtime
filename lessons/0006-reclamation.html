课程首页上一章回收速查

06 / 24 · 给自己造的协程一个完整结局

完成以后，谁来释放栈？

唯一主问题：怎样保证不会在当前栈上释放当前栈？

沿用第 4–5 章共享外壳；这次将自动回收关闭，逐步观察。

“结束了”至少有三个不同意思

inner 返回时，局部资源得到清理；入口仍可能在 fiber 栈上做收尾。入口返回、回到 scheduler 之后，才获得安全释放整块 fiber 栈的机会。外界要读取结果时，又未必还需要这条栈。

本章分开三件事：业务对象生存期结束、切离执行栈、释放栈存储。你会亲自观察它们不是同一个时间点。资源不是靠设置 Done 自动消失的。

A · 分开三个对象

局部对象、执行载体、完成记录

对象存在理由结束/保留边界
Probe 局部对象代表业务资源，构造 live++，析构 live--业务作用域正常返回或同栈异常展开时清理
Fiber 与 Stack承载尚在执行或暂停的调用链必须回 scheduler 后，且不再可恢复，才能释放
Completion记录任务 ID 与异常结果可在栈释放后继续存在；不保存局部对象裸指针

第 1 章已经区分对象与存储，现在用这个区分解释回收。完成记录应拥有需要保留的值，而不是指向已失效栈变量。对象生存期依据见C++ 工作草案；具体回收顺序由本章实验控制。

B · 只允许另一侧收尾

先切回，再 collect

// fiber 的入口一侧：
try { body(); } catch (...) { error = current_exception(); }
state = Done;
// 入口返回，经 uc_link 进入 scheduler

// scheduler 的 step 一侧：
resume(fiber);  // 现在已经回来
if (fiber.state == Done) {
    completions.push_back({id, fiber.error});
    finished.push_back(id);
}
collect();     // 从这里释放 Fiber 和它拥有的 Stack

本章使用 Loop(false) 暂缓最后一步，以便观察。finished 队列是“待释放载体”的清单，不等于外界读取的 completions。collect 只消费前者；消费完成后再次 collect 应为零。

三个边界 ·

① 暂停后：objects=1，stacks=1

Probe 作用域未退出。collect 没有任何 Done 项，不能释放这个 Waiting/Ready 中的暂停栈。

② 入口返回后：objects=0，stacks=1

Probe 已析构，scheduler 得到控制，完成记录已保存。但手动回收尚未发生，栈仍分配着。

③ collect 后：objects=0，stacks=0

载体被释放，完成记录仍在。旧 context 不再有合法的下一段，不能放回 ready。

为什么不能在入口的最后一句先 munmap？因为执行 munmap 之后的返回、函数尾声以及上下文后继转换仍可能需要当前栈。uc_link 的后继语义并不授权提前销毁承载入口的存储。

不要通过“真的提前释放再看看崩不崩”学习。本实验在 fiber 内调用 collect 会先拒绝；验证的是安全前置条件，而不是触发未定义行为。

C · 正常与失败，共用同一回收出口

用三个计数验证完整结局

./labs/build/ch06_reclaim normal
./labs/build/ch06_reclaim throw
./labs/build/ch06_reclaim many
运行前预测完成后核对
paused: objects=1 stacks=1
done: objects=0 stacks=1
collected: objects=0 stacks=0 records=1
[PASS] ch06 normal

throw 也走相同计数序列：异常在 fiber 入口捕获，Probe 在同一栈上展开清理；栈释放后仍能从 Completion 的 exception_ptr 重新抛出 business failure。many 同时创建 64 条协程，暂停时 64/64，结束未收时 0/64，收后 0/0 且 64 个记录。

这些是容器与对象计数，不是 RSS。释放映射、物理内存记账和分配器行为不是本章同一个测量。

构建任务：写出回收前置条件

在个人副本中挖空 collect 的循环，仅保留“不能在 fiber 一侧调用”的检查。根据 finished 中的 ID 找到 Fiber，验证 Done，释放所有权；验证第二次 collect 不重复操作。

然后给 Completion 增加一个由值保存的结果，例如 42，断言 stacks=0 后仍能读取。不要把 inner 局部 int 的地址存进去。最后把任务数改为 1、8、64，检查完成记录数量与栈数量各自的变化。

源码落点与当前边界

本章实验；step / entry / collect。这个教学 Loop 要求把已经启动的协程运行到完成后再销毁；否则析构时明确 terminate，避免静默丢弃暂停栈上的 C++ 资源。这不是通用取消协议。

真实 resumeFiber 从 swap 返回后检查 finishedOnStack，再由 finishFiber 保存 Completion、通知等待者并释放 Fiber。运行库还涉及子任务生命周期，留到第 11–12 章。当前完成记录可能长期保留；“栈已释放”不能推出“所有元数据都不增长”。

唯一过关题

某协程入口已把 state 写成 Done，但尚未返回到 scheduler。此刻能否释放栈？请分别说明此时、scheduler 收到完成以后、collect 以后，业务局部对象、栈、完成结果的状态；为什么保留结果不需要保留整条栈？

作答后自评

不能，仅 Done 标记不足够；入口仍在自己的栈上。body 局部对象已清理，入口返回后 scheduler 才能释放载体；Completion 独立保存需要的结果/异常，因此可比栈活得久。若只说“Done 就 delete”，回到入口还要返回的那一步。

把回收前置条件和结果值变式发给我。到这里，我们造出了可选择、可等待、可结束的协程部件；下一章才加入 Actor 的串行约束。
