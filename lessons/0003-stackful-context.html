03 / 24 · 从保存数据到保存执行现场

保留整条调用链

这次只回答：怎样在深层函数里暂停，而不结束这条调用链上的局部对象？

只运行一个 OS 线程、一个 fiber。不引入 Actor、消息匹配和多个 worker。

先看到第二章做不到的事

第二章的任务能继续，是因为我们手工把进度与数据搬进成员。若 A 调用 body→inner，而暂停点在 inner 深处，普通 return 会逐层结束作用域。要沿用显式状态机，就得继续改写调用链，把所需状态逐层保存。

现在换一种构建路线：给 A 一条独立栈，把尚未返回的函数调用留在那里；暂停时保存以后继续执行所需的现场，换到另一段代码。恢复时加载现场，继续旧调用，而不是从 inner 入口重新执行。

暂停不退出 inner 的作用域；不是“先析构，恢复时再重新构造”。本章要用同一个 Guard 的存活证据验证这件事。

A · 先分清三个真实对象

栈、context、scheduler，各存什么？

对象职责在本实验中
fiber 栈内存为尚未结束的调用链提供独立空间Stack 分配 128 KiB 可用区；A 的 inner 在这里执行
ucontext_t 记录保存/描述恢复现场，包含机器相关上下文及栈描述等fiber_ 与 scheduler_ 是两个不同记录，不是两个线程
scheduler 代码决定何时进入 A，以及回来以后做什么main 手动两次 resume，中间运行 B；不另建线程

getcontext 手册定义 context 结构关系。context 并不是“整条栈的字节副本”；本例的栈一直保留在分配的内存中，切换记录引用该现场。无需现在背机器寄存器列表。

本实验的 thread_local active_ 仅帮助零参数入口找到当前 Demo；它不是调度队列。安全外壳规定同线程、单个活动 Demo，不支持重入或任意跨线程恢复。

B · 唯一新动作：保存一边，进入另一边

读懂 swapcontext 的方向

// scheduler 当前正在执行，准备进入 A：
swapcontext(&scheduler_, &fiber_);

// A 当前正在执行，主动让回 scheduler：
swapcontext(&fiber_, &scheduler_);

规则只有一个：第一个参数保存当前现场，第二个参数提供要进入的现场。以后重新激活保存的现场，就会像那次 swapcontext 终于返回了一样继续。手册：DESCRIPTION 与 RETURN VALUE是本段的原始依据。

这里有两个不同的“返回”：yield 内部的 swap 切走时，scheduler 的 swap 得到继续机会；等第二次 resume，才轮到 yield 内部的 swap 继续，然后 yield 普通返回到 inner。inner 本身没有在暂停时返回。

每一步都问：当前在哪条栈？ ·

① 创建，但尚未运行

getcontext 初始化 fiber 记录；设置独立栈与 uc_link；makecontext 指定入口。构造 Demo 不会调用 body。main 仍在原线程栈上。

scheduler → 准备好的 fiber 入口

② 第一次 resume：进入 A

保存 scheduler_，加载 fiber_。入口执行 body→inner，构造 Guard，value=41。然后 inner 调用 yield。

fiber 栈：entry → body → inner → yield

③ yield：回到 scheduler

保存 fiber_，加载 scheduler_。main 从第一次 resume 得到控制，运行 B；A 的调用链还留在独立栈上，Guard 尚未析构。

正在跑 B；A 暂停，但并未结束作用域

④ 第二次 resume：继续 A

重新保存 scheduler_，加载 fiber_。从 yield 中保存的 swap 后继续，yield 返回 inner。旧 value 加一得到 42，没有再次构造 Guard。

yield 返回 → inner 接着运行

⑤ A 完成：回到 scheduler

inner 返回，Guard 析构；body 返回，入口设置 done。入口返回后按 uc_link 进入 scheduler。main 以后再 resume 时由 done 检查拒绝；栈由 scheduler 一侧的对象析构释放。

完成 ≠ 暂停；已经完成的现场不能再恢复
证据层：首次创建为什么不同于恢复
getcontext(&fiber_);
fiber_.uc_stack.ss_sp = stack_.base;
fiber_.uc_stack.ss_size = stack_.usable;
fiber_.uc_stack.ss_flags = 0;
fiber_.uc_link = &scheduler_;
makecontext(&fiber_, &Demo::entry, 0);

首次还没有暂停位置，因此指定入口；之后由 swap 保存新的恢复位置。上面是说明性摘录，省略了错误分支；运行时使用完整参考实现。uc_link 是入口返回时的后继，不是每次 yield 的目标参数；不要混淆。

该 API 有平台限制，不属于标准 C++17，且已经从 POSIX.1-2008 移除。我们的选择限定在当前 Linux/glibc 框架。本章入口用零参数，避免把指针直接塞进 makecontext 的 int 可变参数。

C · 观察、重建核心、做一个变式

用对象存活验证“未返回”

void inner() {
    Guard guard(*this);
    int value = 41;
    // 记录 A before=41
    yield();
    ++value;
    // 记录 A after=42
}

参考程序先在内存收集事件，再统一输出；你看见的是执行轨迹，不是逐行实时打印。断言检查：构造未执行 body；第一次暂停后 resourceAlive 为 true；第二次完成后为 false；第三次 resume 被拒绝。另检查 value 地址跨暂停一致，但“地址相同”单独不足以证明同一对象存活，必须结合未退出作用域及构造/析构事件。

构建任务 1：补回切换核心

在自己的副本中，只挖空 resume/yield 中的两个 swapcontext 调用，保留完整错误检查与结束保护。合上本页，根据“当前执行者 / 保存目标 / 进入目标”三列补回。先手写方向表再运行，不要通过随机交换参数试错。

构建任务 2：把暂停下沉一层

新增 helper()，将 inner 的 yield 移进 helper；helper 也建立一个带不同名字的 Guard。inner 改为调用 helper，返回后加一。暂停时应该有两层 Guard 活着；恢复后 helper 的先析构，inner 的后析构。

给这条新轨迹写精确断言。验收：B 在两个 Guard 的构造与析构之间执行；两者都只构造/析构一次；重复 resume 不产生副作用。不能为了凑输出把析构日志移到 main。

只在安全外壳内实验。不要释放暂停栈、恢复完成现场、跨线程 resume 或无限递归压栈。取消与暂停状态的安全销毁需要额外协议，第三章没有实现通用方案。
可选工程附录：现在不要求一起掌握

栈空间与释放

教学外壳用 mmap 分配两侧保护页与中间可读写栈区。若页大小为 P，可用区为按页向上对齐的 U，总分配字节数为 U+2P；P=4096、U=128 KiB 时，总计 136 KiB。这里说的是地址空间映射大小，不等于立即占用的物理内存。完整 mmap 机制留待栈管理专题。

保护页不能保证所有栈溢出都可安全恢复。入口还在自己的栈上时不能释放它。本例总会恢复到完成，再回到 main 析构 Stack；它没有解决“用户把仍暂停的 Demo 直接销毁”这一通用 API 问题。

异常桥接

./labs/build/ch03_ucontext --throw

本例的异常在 fiber 入口 try/catch 中被捕获，同栈展开清理 Guard，存为 exception_ptr；main 回来后再重抛。切换上下文不等于跨两条栈的 C++ 异常展开。不要删掉入口捕获，让异常逃过 context 入口边界。

实际框架映射，只认位置

internal.h 的 Fiber 保存 fiber context 和栈，Worker 保存 schedulerContext；actor_system.cpp 中 resumeFiber 切入；coroutine_context.cpp 中 await 切出。await 还做登记、结果检查和取消处理，不能直接等同裸 yield。当前框架把 FiberId 拆为两个 32 位参数传入入口，并从 currentFiber 取得对象；不同于教学零参数入口。

唯一过关题 · 闭卷追踪一次往返

main 第一次 resume A，A 在 inner→helper 中 yield，然后 main 运行 B，再第二次 resume A。请逐次说明：当前在哪条栈，保存到哪个 context，加载哪个 context，恢复后从哪里继续；据此解释 B 执行时 inner 与 helper 的 Guard 为什么未析构，以及整条 A 完成后为何不能第三次直接切回旧现场。

作答后：检查最小完整链

main：保存 scheduler、加载 fiber；yield：保存 fiber、加载 scheduler；第二次 resume：保存 scheduler、加载 fiber，继续 yield 的 swap 之后，再普通返回到 helper。暂停没有退出 helper/inner，Guard 仍存活；完成则退出这些作用域并通过入口后继回 main。完成的旧现场不再是可继续的活调用，因此必须由 done 拒绝再次切入。若把第一次与第二次 resume 都说成“从 entry 开始”，回到第④步。
