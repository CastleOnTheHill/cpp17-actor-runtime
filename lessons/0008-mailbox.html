08 / 24 · 让任务从消息中产生

一条消息怎样抵达处理点？

唯一主问题：发送被接受之后，还必须发生什么，业务才真的完成？

只构建一个 Actor 的邮箱与类型检查。暂不引入广播等待或关联响应。

把第七章的“任务编号”换成消息

第七章由多个 worker 领取任务编号，再调用同一个 Actor。现在发送者交付的是一份内容：例如 Add{2}。我们需要一个邮箱，在发送者返回以后仍持有消息，直到 Actor 有机会处理。

你的产物是一个有容量限制的小邮箱。它会故意接受一条载荷类型错误的消息，让你观察“接受”“消费”“应用业务”不是同一个事件。

A · 消息是什么对象

约定编号与实际载荷，两者都要检查

struct Add { int amount; };
struct Message {
    int type;         // 本章约定 1 表示 Add
    std::any payload;
};

type=1 只是协议约定，不会强迫 std::any 自动存入 Add。发送者仍可能装进 string。接收者先检查消息种类，再检查实际载荷；不能因为编号正确就假定 any_cast 一定成功。

if (message.type != 1) { ++badType; return; }
const Add* add = std::any_cast<Add>(&message.payload);
if (!add) { ++badPayload; return; }
value += add->amount;

本章选用指针形式的 any_cast：类型不符时得到空指针，显式走错误分支。不要把它与返回值/引用形式的异常行为混淆。

消息必须比发送栈帧活得久

实验 post 按值接收 Message，再移动进 deque。Add{2} 被复制到 any 后，发送者把原 Add 改为 99，邮箱里的值仍为 2。这个结论限于这样的值类型；把 shared_ptr 或裸指针装进 any，不会自动深拷贝其指向对象，也不会凭空建立生命周期与线程安全保证。

B · 两条锁边界，三个业务里程碑

接受、消费、应用

里程碑发生了什么还没证明什么
Accepted容量与关闭检查通过，消息入队没证明 handler 已运行，也没证明载荷有效
Consumedworker 在 Actor 执行边界内取出一条消息没证明业务接受该种类或载荷
Applied类型检查通过，执行 value += amount只证明本章同步加法完成；不代表复杂异步工作流最终成功
// 发送者：只用 mailboxMutex，短暂检查并入队
post(message);

// worker：executionMutex 覆盖整个业务片段
lock(executionMutex);
{ lock(mailboxMutex); pop_one_message(); unlock(mailboxMutex); }
validate_and_handle();
unlock(executionMutex);

mailboxMutex 保护队列结构；executionMutex 保护同一 Actor 的处理过程。处理时已经不持有邮箱锁，发送者可以继续入队。当前教学路径不会先持有 mailboxMutex 再去锁 executionMutex；自行增加反向嵌套，会带来新的死锁风险。

本实验在所有发送完成后才启动 worker，因此“邮箱空则 worker 退出”在这些测试里成立。真实运行时若未来仍可能来消息，worker 应等待通知或新的调度 job，而不是看到一次空队列就永久退出。

接收函数的返回值必须有精确含义。Accepted 是入队承诺，不是业务成功回执；若需要后者，必须定义额外响应协议，第 10 章才构建。

C · 一次完整投递实验

让错误也走完整路径

按顺序发送：Add{2}、type=1 但载荷为 string、type=9 的未知消息、Add{3}。关闭新入口后启动 worker，把已接收消息排空。先分别预测 consumed、applied、badPayload、badType 和 value。

写完预测后核对

1 与 4 worker 模式均为 consumed=4、applied=2、badPayload=1、badType=1、value=5。程序先断言 post 后尚无业务执行，并验证原 Add 改成 99 不影响消息中的 2。

capacity 模式容量为 1：第一条接受，第二条被 Full 拒绝；消费第一条后再次发送成功。close 后拒绝新消息，但继续排空已接收内容。最后 consumed=2、applied=2、value=5；Full 的那次尝试不计入消费。

这里的 close/drain 与容量 1 都是教学策略，不应套用到当前框架的 shutdown 或邮箱容量；看公开接口与源码才能确认。

在个人副本中挖空 post 的 Closed/Full 分支和 dispatchOne 的类型检查，用上面的承诺补回。再新增 Set{value} 与种类编号 2：发送 Set{10}、Add{2}，最终应为 12。刻意给 type=2 配 Add 载荷，断言它被消费但不应用。

真实框架的路径与教学删减

教学实现没有 Actor 注册表、消息 ID 或通知队列。当前框架 Message 还含 typeId、id、correlationId、sender，MessagePtr 是 shared_ptr<const Message>。const 封装同样不保证 payload 指针所指数据不可变。

在 ActorSystem::send 与 processJob 中寻找 mailbox.push_back、DispatchMessage、mailbox.pop_front、notifyMessage、onMessage，逐个对应“入队、安排处理、取出、通知等待者、处理消息”。notifyMessage 的广播匹配留到第 9 章；不要现在把它假定为只能唤醒一个人。

真实 send 返回 MessageId，而非本实验的 Accepted 枚举；这个 ID 也不是业务成功回执。teaching 分支的 mailbox 没有本实验的固定 capacity，也没有同名 close/drain 接口。我们加入容量，是为了让 Accepted 与拒绝的边界可观察，而不是修改真实运行库。

唯一过关题

发送者得到 Accepted，接收方后来发现 type=1、payload 却是 string。请沿“消息所有权→入队→消费→校验→业务应用”说明这次发生了什么、没发生什么；如果发送者要确认业务完成，为什么不能仅检查 Accepted？

作答后自评

邮箱接管了消息并允许异步取出；消费计数增加；载荷检查失败，badPayload 增加，applied 与业务 value 不变。Accepted 只记录前面的入队事件，不能携带尚未发生的处理结论。要证明业务完成，需要在处理结果产生后额外通知。若把消费等同成功，重做四消息五计数实验。

把投递轨迹、计数预测与 Set 变式发给我。第 9–24 章仍是规划，当前不要求越过未掌握的章节；我们可以回到你正在做的第二章继续逐题辅导。
