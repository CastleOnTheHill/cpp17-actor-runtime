从调度到邮箱

04 · Ready 与选择

Ready 表示有资格被恢复；Running 表示已经选中并切入。FIFO 调度：取头、恢复、交回后检查状态、必要时入尾。不交回控制的业务不能由修改队列来抢占。

教学不变量：Ready 的 ID 在队列恰好一次，Done 不再入队。回第四章。

05 · Waiting 与唤醒

Running --登记并切出--> Waiting
Waiting --条件满足--> Ready --被选中--> Running
Running --业务与入口结束--> Done

ready 空不等于所有协程结束。模拟 deadline=now+duration；advanceTo 只使到期等待者入队，step 才恢复。tick 不等于秒；同期限顺序与零时长行为由实现规定。回第五章。

06 · 完成与回收

业务作用域清理 → 入口完成 → 回 scheduler → 保存 Completion → 从 finished 清单释放 Stack。先有另一条有效执行栈，才可释放旧栈；不能用 Done 标记代替切离。

栈数下降不代表完成记录被清空，也不等于 RSS 的相同变化。回第六章。

07 · Actor 执行令牌

在当前教学中，“令牌”指 execution mutex 的独占所有权。安全出队只保证任务分配不重复，不能代替 handler 全片段的状态保护。OS 暂停线程不自动释放锁。

实际框架以 processJob 为边界，await 切回后收尾解锁；跨 await 的业务状态可能被其他片段修改。回第七章。

08 · 邮箱的三种结果

事件证明不证明
Accepted已入队已处理、载荷有效
Consumed已取出业务应用成功
Applied本章加法已执行复杂异步需求最终完成

mailboxMutex 保护队列；executionMutex 保护处理片段。type 编号不会强制 any 中存储的 C++ 类型；普通值复制与指针指向对象的共享必须区分。回第八章。

不要从教学模型推断的承诺

全局 FIFO、公平延迟、精确计时、通用取消、安全跨线程恢复、异常自动回滚、消息深度不可变、固定邮箱容量、close/drain 停机语义，都不是由这五个小实验自动证明的真实框架性质。
