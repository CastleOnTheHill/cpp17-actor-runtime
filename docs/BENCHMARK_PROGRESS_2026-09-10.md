# 当前性能水平与开源框架对比（2026-09-10）

> 后续最终验收已完成：紧凑 ready 队列版本的五轮完整 SO5 吞吐门槛为 **12/12 通过**，
> 最弱配置 **82.37%**；最终行覆盖率 **97.45%**。尾延迟尚未全面追平。
> 见 [最终验收报告](SCHEDULER_ACCEPTANCE.md)。下文保留 a7bb1a7 阶段的三框架对比快照，
> 其中 11/12 和 97.44% 是该阶段数据，不是后续最终状态。

结论：**事件消息吞吐已经具备竞争力，但性能仍不均衡，不能宣称全面达到成熟框架水平。**
当前 SO5 完整长测有 11/12 个配置达到其吞吐的 80%，仍有一项只有 77.70%；
多 worker 有明显收益，但尾延迟、热点、fiber 和 IPC 必须分别看。

## 当前代码的三框架同机实测

不是引用互联网排行榜，也不是把优化前的 CAF 数据与当前代码拼接。
五轮固定预算、串行随机顺序、本机 WSL、CPU 集合 0–7、64B、window1、batch1。
每轮 1w/1c 共 600 万次往返；4w/8c 共 1200 万次往返。表中都是五轮中位数。
RPS 指完整请求—回复往返/秒，逻辑消息投递量约为两倍；p99 是各轮 p99 的中位数。

| 配置 | 本框架 | CAF 0.19.6 | SObjectizer 5.8.3 |
| --- | ---: | ---: | ---: |
| 1 worker / 1 对，RPS | 3,071,855 | 2,488,518 | 3,611,485 |
| 同配置 p99（µs） | 0.653 | 0.853 | 0.582 |
| 4 worker / 8 对，RPS | 3,615,531 | 5,919,930 | 1,334,100 |
| 同配置 p99（µs） | 7.169 | 1.280 | 8.588 |

- 单 worker：吞吐比 CAF 高约 23%，比 SO5 低约 15%；延迟也是介于两者之间。
- 4 worker / 8 对：吞吐约为 CAF 的 61%、SO5 的 2.71 倍；p99 仍是 CAF 的约 5.6 倍。
- CAF 多 worker 五轮范围为 521–684 万 RPS，宿主机噪声不能忽略。
- 这只是指定版本、调度器、batch1 和拓扑的比较。旧基线已证明增大对照框架 batch 会改变排名；
  不能从这里推导本框架胜过所有 SO5 配置，也不能外推生产容量或行业排名。

证据：[五轮原始数据与汇总](../benchmark-results/2026-09-09-scheduler/actor-scheduler-compat-confirm-20260910/summary.json)，
[六个二进制的哈希及环境](../benchmark-results/2026-09-09-scheduler/actor-scheduler-compat-smoke-20260910/environment.json)。

## SO5 完整验收仍未全部通过

另外一组完整矩阵是 12 配置 × 2 框架 × 5 轮，每轮 400 万次往返。
未达标项：1 worker / 8 对 / window16，2,813,253 对 3,620,627 RPS，**77.70%**。
该差距在先前短测中也出现，不通过重跑或四舍五入隐藏失败。

尾延迟也不能只看吞吐：4 worker / 8 对 / window16 的本框架 p99 为 177.014 µs，
SO5 为 101.978 µs，约 1.74 倍。共享热点的本框架吞吐约为 SO5 的 95%，p99 则更低。

## Fiber、IPC 与正确性

五轮固定预算补测中，4 worker / 8 fiber 客户端达到 814,011 RPS，p99 为 118.433 µs；
4 worker / 64 客户端达到 1,263,656 RPS，p99 为 177.294 µs。
这是保留有栈等待和 owner 绑定恢复的成本，不能与 CAF/SO5 普通 handler 当作等价功能比较。
单 fiber 的 6000 次补测仅约 32–41 ms，不能据此宣称长期稳态容量。
另已完成 [13 配置、三轮 fiber/IPC 矩阵](../benchmark-results/2026-09-09-scheduler/actor-scheduler-fiber-ipc-matrix-20260910/summary.json)，
各配置按约一秒独立校准，不能与固定请求预算的补测混成一组排名。
该矩阵中单 worker / 单 fiber 为 891,950 RPS、p99 2.192 µs；
4 worker / 单 fiber 为 164,837 RPS、p99 122.730 µs。
64 客户端仍有 78.9–133.9 万 RPS 的跨轮波动，长期稳定性还不能据此保证。

真实跨进程、64B、单客户端五轮中位数：本框架 **10,508 RPS / p99 176.249 µs**，
裸 Unix DGRAM **29,959 RPS / p99 75.105 µs**。IPC 固定路径仍有显著差距。
裸 socket 不提供相同的 Actor 寻址、关联回复与生命周期语义，协议头和线程结构也不同。

三轮配对的全采样唤醒诊断：无额外 pulse 为 153,627–179,656 RPS，p99 为 113.494–122.726 µs；
有每毫秒 pulse 为 135,864–173,542 RPS，p99 为 115.397–140.756 µs。
本轮没有再观察到旧基线的约 10 ms p99 台阶，也没有依赖 pulse 才能运行；这不是生产空消息方案。

当前代码 ASan/UBSan 下 12/12 测试通过；运行库全部 src/include 可执行行覆盖率
**1178/1209 = 97.44%**，没有源码排除。原始 gcov 分支覆盖率为 62.41%，包括异常边，
不能把行覆盖率当成分支覆盖率或竞态安全证明。

## 接下来具体优化什么

1. 单 worker 大窗口的固定开销，使全部 12 项吞吐达到原有门槛。
2. 多 worker 排队公平性及 p99，不能只追吞吐。
3. 分开分析 fiber 恢复与 IPC 桥接成本；它们不是同一条普通事件路径。

当前单 worker / 8 对 / window16 的新 profile 有 1407 个样本、0 丢失；
原始 script 事件数等于折叠权重，SVG 已通过 XML 解析。用户态 on-CPU 叶节点中，
mutex lock/unlock 合计 18.76%，sendOwned 11.73%，processJob 7.68%，deque emplace 4.19%。
这些不是端到端耗时占比，也不能直接加总为可实现的优化收益。
